Step 3: D1 interface and legacy removal

Implemented locally October 5, 2026. Migration plan · Target requirements · Data and authorization foundation

Later progress: Step 4 launch features are now implemented locally. This page records the step 3 baseline; the step 4 page has current validation and release gates.

Catalog data now comes from D1

The reference catalog reads normalized releases, active parts, file cards, related releases and media metadata through the new D1 services. Search, line/year filters, pagination and totals operate on stored records. An empty catalog remains empty until the administrator enters records; there is no fallback dataset, scraping or automatic reseeding.

The interface uses the G.I. Jeff's Files name, always-visible search and collapsed filters. Anonymous users can browse releases, expected parts, file-card text and entered reference photos. Signed-in collectors can open their collection or view unowned releases. Parts-only and ownership-unconfirmed holdings remain in the unowned view; confirmed ownership excludes that release.

Legacy pieces, accessory-image, reference-photo and related-version URLs now read D1 metadata or redirect to authorized media delivery. Legacy catalog audits return a retired response after checking administrator access. The market route reports that valuation is not yet available; it no longer fetches reference-site pages or fabricates price estimates.

Collection editor uses the normalized model

Each saved record represents one copy. Collectors can add a release or unidentified item, edit condition, completeness, packaging, sealed status, ownership, private notes/location, part quantities and unidentified accessories, upload photos, reorder the cover image, and delete a copy. The existing camera uploader and zoomable photo viewer are reused with authorized media URLs.

Blank quantity means unknown; zero means absent. A new Complete choice fills known expected quantities and marks original packaging present without assuming sealed status or Mint condition. Partial and Not sure start with unknown quantities. Changing the choice on an existing copy preserves recorded quantities. The server validates Complete against the parts list.

Opening an existing copy incorporates newly added catalog parts as unknown quantities and prompts review of a changed catalog revision. Recorded quantities for retired parts are preserved. Editor submissions include only accepted normalized fields and preserve existing private acquisition facts.

Removed source dependencies

  • Bundled catalog, enrichment, identity, reliability and accessory-image JSON payloads.
  • Old static catalog helpers, research galleries and audit/report pages.
  • Research import/enrichment scripts, scraped fixtures and their obsolete tests/documentation.
  • The bundled reference-photo directory.

Historical source provenance remains documented. The four legacy database tables and original applied migrations remain in place until the controlled reset step. No production database rows, R2 objects, access settings or hosting bindings were changed. This step was not deployed.

Local setup and validation

After installing dependencies, run pnpm db:local before pnpm dev. The helper applies checked-in SQL migrations to the checkout's local Miniflare D1 database using the placeholder database ID and an explicit --local argument. Its generated configuration and local storage are ignored by Git. It initializes schema only and does not insert catalog records or reset existing local data.

node scripts/check-step2.cjs exercises the actual API handlers against isolated real SQLite and test R2 storage. Step 3 extends coverage to empty catalogs, search, filters, pagination, ownership filtering, normalized editor round trips, quick choices, entered reference media and retired audit/valuation routes. node scripts/check-photos.cjs checks photo ordering, deduplication, cover selection and removal.

TypeScript validation and the production build pass. The build retains the framework's route-classification advisory. The local page returned HTTP 200. The initial catalog request identified an unmigrated local database; all three local migrations subsequently applied successfully.
