The highest-risk gap is application authorization. Existing owner-only hosting protects the current deployment, but its unscoped collection and photo reads are unsuitable for a public multi-user site. Private notes, purchase costs, photos and authenticated email must not cross user boundaries.

Confirmed reset scope

The owner has directed that all existing application data be deleted. Replace conversion, backfill, reconciliation, legacy-ID redirects and preservation work with a clean start. This includes the existing reference catalog, not only the owner's collection.

  • Delete all rows from the existing D1 application tables: items, settings, catalog_issues and catalog_checks. Remove obsolete tables through inspected schema migrations when appropriate.
  • Delete existing application file contents from the Site's R2 bucket, including collection uploads and catalog media, and remove their metadata references.
  • Remove bundled catalog/enrichment datasets, accessory inventories/images, alias maps, curated identity data, audit datasets, guide prices and any legacy seed/import mechanism that would repopulate them.
  • Retain reusable application code, generic UI assets, repository history, planning documents, hosting identity, runtime authentication configuration and DB/BUCKET infrastructure. These are not application records.
  • Initialize the new schema with no catalog releases or holdings. Provision the administrator from the verified runtime identity. The owner enters or imports new catalog data; test fixtures stay out of production.

No legacy data backup or conversion is required for this reset. Normal backup/export and recovery requirements apply to new data after implementation. The authorized live reset was executed October 6, 2026; see the step 5 release record.

The reset is an authorized destructive implementation step. No preservation adapter, copy-splitting reconciliation, alias conversion or legacy-photo compatibility layer is required. Existing applied migrations remain immutable; new migrations describe the target schema.

Required release gates

  • Clean state: No legacy rows, media contents, bundled catalog records or repopulation jobs remain in the active application. Newly created admin configuration is distinct from deleted inventory.
  • Isolation: Collector A cannot read, modify, export or delete collector B's private records or photos, even using guessed IDs or direct requests. Anonymous requests receive catalog data only. Login email and private fields never appear in aggregate or public responses.
  • Visibility and caching: Signed-in public collection views work; making a collection private removes access to records and media. Private responses and caches cannot leak across identities. Mutations enforce ownership and request-origin protections.
  • Domain rules: Test new fixture entries for Snow Job with two skis and zero figure, an owned incomplete multipack, ownership-unconfirmed inventory, two differently conditioned copies, Complete versus Loose rules and catalog part revisions.
  • Data interchange: New imports/exports preserve blank/null/zero distinctions and copy identity. Repeated or failed imports cannot create unintended duplicates. Export plus media can restore newly created collections.
  • Production readiness: Build and relevant authorization/domain tests pass; empty-schema initialization works; published desktop/mobile and sign-in workflows work. Record storage limits and remaining provider dependencies.

Recovery after the reset

The reset intentionally has no legacy-data restoration path. Reverting code must not bring back removed catalog datasets or restore the old unscoped APIs. If deployment fails, keep the Site owner-restricted and repair or redeploy the new application against the empty target schema.

Once new users begin recording data, establish normal backup/export, media recovery and deletion-aware retention procedures. Protect that new data during subsequent releases. A code rollback does not reverse database changes.
