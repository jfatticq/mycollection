Characters and factions

G.I. Jeff · October 18, 2026 · Requirements

Catalog editing

Characters are a list of named associations: zero, one, or many. Each can optionally reference a catalog part of the same item (including a preserved historical part). Multiple copies of the same character may link to different parts. Names use suggestions from existing catalog associations, with write-in values supported; these are not a separate global character-directory feature.

Factions are multiple direct tags backed by faction taxonomy terms. Select existing terms or add a new name; a new faction is created only when the catalog item is saved. Generic taxonomy checkboxes exclude factions to keep one faction selection interface. Removing a part clears its optional character link while retaining the character name.

There is no hardcoded faction affiliation or seeded character list. To configure the example, create Cobra and Dreadnoks, then edit Dreadnoks in Taxonomy and select Cobra as its parent. Tag items Dreadnoks without also requiring Cobra. Mixed-faction sets can carry several direct tags. Parent relationships are site-wide, and changing one affects filtering for all tagged catalog items.

Filtering and display

Public item details display character names with any linked part labels, and direct faction names with parent context. Search includes all associated character names. Exact character-name filtering is supported by the catalog API. The faction dropdown and faction taxonomy filters include descendants at any depth; choosing a subgroup excludes items tagged only to its broader parent. Collection filtering includes inherited faction IDs/names without exposing private holdings to others.

Faction parents must be faction terms and cannot form a cycle. Duplicate names differing only in ASCII case are rejected by the taxonomy editor. Referenced factions retain their faction type. Existing faction parents are preserved when item saves reuse those terms.

Persistence, compatibility and transfers

Additive schema migration 0006_brave_risque.sql creates release_characters with a composite part/item foreign key. Factions reuse taxonomy and release_taxonomy. Existing migrations are unchanged, and no catalog rows or files are deleted.

Legacy singular strings remain readable and filterable until an item is saved using the new model. They are preserved as one name each; commas are not split automatically. Explicit empty arrays clear the corresponding values. CSV/JSON templates and exports carry characters objects with name/optional partId, and factions as names. Legacy singular import fields remain accepted. New faction terms use deterministic IDs so repeated names in a single atomic import share one term.

Revisions include both arrays. Duplicate merging unions character associations and factions, maps character part links through the reviewed part mapping, and preserves links to retained historical parts. Character names on unchanged retired/source records remain historical catalog data.

Faction suggestions and editor actions

The faction picker includes G.I. Joe, Cobra, Dreadnoks, Iron Grenadiers, Oktober Guard, existing faction terms, and Other… for an inline custom name. Custom text updates the saved draft directly; there is no separate New Faction Name field. Suggestions become taxonomy terms only when saved; affiliations are not assigned automatically.

Save persists catalog fields and keeps the editor open. Save & Close closes only after a successful write. A failed save leaves the draft and error visible. Close w/o Saving sends no write and discards unsaved catalog fields. Both submit buttons use native form validation. Photo uploads, removals and cover changes continue to save immediately, with an explanation beside the photo controls.
