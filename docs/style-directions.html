Design system / selected direction

Digital camo, built for collectors.

G.I. Jeff's Files combines a charcoal workspace, a restrained pixel-camo masthead, sage accents, and solid white content panels. The toys, their parts, and their history should always be the focus.

This replaces the earlier comparison of three style directions. It documents the current implementation and sets design requirements for future screens. Accessibility and responsive review rules below are targets, not a claim that every screen has passed a complete audit.

1. Identity & design principles

Recognizable, restrained, useful

  • Use digital camo in the masthead; keep forms, photos, and tables on solid surfaces.
  • Use familiar collector tools and plain labels. Let photographs provide most of the color.
  • Keep the main action obvious. Group specialist administration tools away from everyday editing.
  • Favor readable density on desktop while keeping every workflow usable on a phone.

Identity rules

The site name in prose is G.I. Jeff's Files. The masthead wordmark is G.I. JEFF'S FILES.

Use a system sans-serif throughout. Avoid stencil body text, distress effects, decorative military ranks, and camouflage behind data.

Keep the footer description: Unofficial G.I. Joe collector catalog. The visual identity should not imply an official brand affiliation.

3. Camo & masthead

The repeat is an 80 × 64 px SVG tile. Base #3d473a, lighter blocks #4e5746, darker blocks #2b342d, and a #111a1455 overlay keep the white lettering readable.

Header specification

  • Minimum height: 108 px. Wide-screen padding: 24 px vertically and 48 px horizontally.
  • Bottom rule: 3 px sage. Keep the pattern at its native repeat size.
  • Wordmark weight: 850. Navigation weight: 700. Text: #f4f6ed.
  • Text shadow: 0 1px 2px #0b120b, 0 0 5px #0b120b. Keep it subtle, not a luminous glow.
  • At narrower widths, reduce padding and wrap navigation. Avoid horizontal overflow or overlapping labels.

Use the tile already embedded in digital-camo.css; do not introduce a different pattern for each page.

5. Layout & spacing

Workspace hierarchy

  1. Shared camo masthead and navigation.
  2. Page title and short guidance.
  3. Summary or section navigation when useful.
  4. Search and primary actions.
  5. Cards, tables, editor, or empty state.
  6. Pagination and footer.

Spacing system

Use a 4 px rhythm for new work: 8, 12, 16, 20, 24, 32, and 48 px. Use 12–16 px between related controls, 20–24 px inside panels, and larger gaps between major groups.

Page maximum width: 1500 px. Gutters: 48 px wide, 24 px at ≤1050 px, 16 px at ≤750 px.

Base corner radius: 6 px. Paper panels and cards use a 1 px border; selected content panels add a 4 px sage left accent. Existing components may retain larger radii.

Dialogs use solid white surfaces and a bounded, scrollable height. Keep titles and actions reachable on small screens. Group long editors into named sections. Use subdued hover shadows on cards; avoid decorative gradients in content panels.

6. Buttons & forms

Use one prominent primary action per local task. Secondary actions use white outline controls. Destructive actions need specific language and a clear explanation of the consequence.

Button specimens

Controls have a 44 px minimum target height. Use 18–20 px outline icons alongside text when helpful. Disabled controls are dimmed and unavailable; explain a prerequisite nearby when it is not obvious.

Keep labels visible; placeholders are examples or hints. Place errors beside the relevant field and provide a summary for long forms. Preserve entered values after a validation failure. Condition choices need tooltip guidance available on keyboard focus and touch, not hover alone.

Interactive examples are local demonstrations. Nothing is saved.

7. Navigation, search & administration

Search remains visible. Filters start collapsed and expand on request. Keep catalog, collection, and administration contexts distinct.

The search icon replaces the visible label inside the control; the input retains an accessible name. This guide's search field is illustrative.

Pagination specimens

Navigation behavior

  • Administration opens on Catalog items. Its four tabs use a sage fill for the active tab.
  • Main catalog view switches currently use a sage underline, rather than filled admin-tab styling.
  • Tab controls support arrow keys, Home/End, visible focus, and tab/panel relationships. Hidden panels must not remain keyboard-accessible.
  • In the application, preserve unfinished admin input when switching sections. Current panels remain mounted while inactive content is hidden.
  • Admin pagination uses labeled arrow icons. Hide unavailable directions; with zero releases, show the count without arrows. This update is currently scoped to administration; apply the same rule when updating other paginated views.

Image rules

  • Use a consistent photo well with #eef1e9 behind images.
  • Contain the full toy or part; do not crop away identification details.
  • Keep original photo colors. Do not tint, blend, or overlay camouflage on catalog imagery.
  • Provide meaningful alt text for release, part, and file-card images. Decorative placeholders should not repeat adjacent text.
  • Use a clear missing-image state. Support multiple release photos, part images, and readable file-card images and text.
  • Image viewers need labeled close controls, keyboard operation, and a scrollable small-screen layout.

9. Feedback & interface states

Empty

No releases yet.

Add your first reference release to start the catalog.

Loading

Loading catalog…

Keep the layout stable and identify the work underway. Announce status without repeatedly moving focus.

Success

Example message: Release saved.

Confirm the completed action. Keep feedback near the task and available to assistive technology.

Error

Example message: Could not save this release.

Keep your edits and try again. Explain a fix when known; do not report success before the operation completes.

Warning specimen: This action affects linked records. Review the selected releases before continuing.

For inaccessible content, explain the access requirement and offer sign-in where appropriate. For destructive confirmation, name the affected item and consequence. Avoid generic “Are you sure?” text. Use role="status" for routine live updates and role="alert" for urgent errors in the application; the static specimens above do not announce themselves as new errors.

Responsive review

Check at 1440, 1024, 768, 390, and 320 px, and at 200% zoom. Navigation must wrap cleanly, labels must stay with controls, and actions must remain reachable. Avoid page-level horizontal scrolling; use contained scrolling for wide tables. Long release names and identifiers must not force overflow.

12. Accessibility requirements

  • Target WCAG AA contrast: 4.5:1 for normal text and 3:1 for large text; review control boundaries, focus indicators, and chart marks too. Measure new pairings, including text over the camo pattern.
  • Keep visible keyboard focus. Current outlines are 3 px with a 3 px offset: sage on charcoal and olive within light editor/panel surfaces.
  • Use semantic headings, buttons, links, labels, landmarks, and table headers. Every icon-only control needs an accessible name; decorative SVGs use aria-hidden="true".
  • Maintain 44 px touch targets where practical. Support hover, focus, active, disabled, and busy states.
  • Tabs need arrow-key navigation and a single tab-stop entry. Dialogs need managed focus, a labeled title, focus restoration, and Escape dismissal when safe.
  • Do not rely on color alone for selection, errors, ownership, or value changes. Pair visual treatment with text or structure.
  • Make tooltip guidance accessible by keyboard and touch. Essential information must also be available without hovering.
  • Respect reduced-motion preferences. Avoid flashing, animated camo, and motion that delays a task.
  • Provide image descriptions and a data alternative for charts. Test screen-reader names and keyboard order on real application screens.

Legacy token names

--armory-navy now maps to olive #526344; --armory-brass maps to muted green #718258. Do not infer blue or gold from the old names. Primary-button styling explicitly uses sage with dark text; generic primary tokens alone do not describe every themed control.

Review checklist for a new or changed screen

  1. Confirm the user's task, permissions, and one clear primary action.
  2. Reuse the shared header, theme colors, and appropriate card, panel, form, or table treatment.
  3. Check realistic content: long names, unknown quantities, missing photos, multiple parts, empty results, and failures.
  4. Verify accessible names, focus order, keyboard interaction, touch targets, contrast, and zoom.
  5. Check the responsive sizes above and confirm no unreachable controls or accidental horizontal overflow.
  6. Verify success and error feedback against the actual operation. Update this guide if a reusable pattern changes.
