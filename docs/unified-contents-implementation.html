Catalog editor

A single Contents / Parts editor supports any number of figures, vehicles, accessories, other physical parts, packaging and paperwork. Each row has a name, physical type, expected quantity, independent Main Component flag, optional parent grouping, optional catalog reference, and character associations. Expected quantities remain absolute per retail catalog item; a parent does not multiply them.

Quick actions add each type of part. Figure/vehicle main-component defaults depend on the retail item type, and remain editable. Packaging and paperwork cannot be main components. Parents exclude the row and its descendants; a parent with children cannot be removed until those children are reassigned or removed.

Characters are entered on part rows using existing-name suggestions or write-in values. An unfinished name must be added or cleared before saving. The item summary reflects all associations without asking for duplicate entry. Existing associations without a current part appear under Characters Needing Placement; they can be assigned or explicitly removed. Removing a part preserves its associations for reassignment. Existing faction behavior remains separate.

Part images display on their rows. Save a new item/part, then use Reference Photos to upload or manage images for that part. Photo changes still save immediately; catalog field changes use the existing Save, Save & Close and Close w/o Saving actions.

References and related releases

Reference Catalog Item is an optional searchable selector on a part. Selecting it only records a reference. It does not import the other release's weapons, packaging, file cards or part quantities, and creates no owned collection copies. Self-references are rejected. Existing references are preserved.

Related Releases is a distinct section for variant, repaint, international, packaging and general relationships. Add Related Release uses the same name/year selector; raw catalog IDs are no longer required in the UI. Related links describe releases rather than box contents. Pending search text must be selected or cleared before form submission.

Public detail pages display physical type, main-component status, grouping, quantities and navigable component references. Existing character/faction search behavior and related-release navigation are retained.

Storage and compatibility

Migration 0007_abnormal_green_goblin.sql adds nullable part_type and main_component columns. It performs no data backfill and deletes nothing. Existing IDs, owned quantities, images, characters and reference links remain stable.

Old records use their existing primary/accessory/packaging/paperwork role when new fields are null. A legacy primary component can be identified as Figure or Vehicle from its retail item type; ambiguous legacy multipack/playset primary parts remain Other Part until edited. An old accessory row is not guessed to be a driver. Saving persists the explicit type and main flag.

The API and CSV/JSON parts arrays support partType (figure, vehicle, accessory, packaging, paperwork, other) and mainComponent (boolean). Legacy kind remains accepted and is derived consistently for older clients. New exports include both dimensions. Character associations retain the existing characters array with scoped partId, keeping transfers and revisions compatible.

Collection ownership uses main-component quantities independently of physical type: a vehicle driver can be a Figure without confirming ownership of the vehicle. Completeness still requires every verified expected part and original packaging. Existing copies are not duplicated or recalculated automatically; catalog revisions continue to flag them for review.

Duplicate merging requires matching physical types and ownership roles, or explicit historical preservation. Preserved rows retain type, main flag, references, character links, media and owned quantities.

Removal controls and faction colors

Factions and characters use bordered light groups; parts, file cards, related releases, unplaced characters and reference photos use matching light cards. Icons retain existing callbacks and disabled guards. Desktop buttons are 28 px with 14 px icons; coarse-pointer targets expand to 44 px.
