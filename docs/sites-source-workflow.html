Local development

Use Node.js 22.13 or later and pnpm 11.25.0, as declared by the imported application. Preserve pnpm-lock.yaml; do not substitute npm or regenerate dependencies merely to move the source.

  1. Configure this checkout as portable with the installed Sites plugin's scripts/configure-execution-profile.mjs. Its configuration is ignored and stays local.
  2. Install with pnpm install --frozen-lockfile. The upstream install:ci wrapper uses Linux utilities; on Windows use pinned pnpm directly.
  3. Apply local schema with pnpm db:local, then use pnpm dev for local preview and pnpm build for the portable build. Local state stays under ignored .wrangler/; never copy it to production.

GitHub and Sites synchronization

GitHub is the canonical implementation repository. Keep Sites publishing in a separate checkout opened through the native Sites workflow so its existing Git ancestry is preserved. Never force-push this unrelated GitHub history into Sites or replace the GitHub origin with the Sites remote.

  1. Before publication, finish and commit the implementation to GitHub through the normal branch/review process. Record the exact reviewed GitHub commit. Check current Sites version and open the same hosting project into a separate empty checkout using the native Sites source credential and bundled site-workflow.mjs. Credentials belong only in hidden stdin/session memory.
  2. Compare Sites changes since the last synchronized production commit. If another editor changed the Site, reconcile those changes into GitHub before overwriting files. Do not discard concurrent edits.
  3. Transfer tracked deployable source from the reviewed GitHub commit into the opened Sites checkout. Include the hosting manifest, application source, configuration, lockfile, migrations, scripts and required public assets. Carry intentional file deletions too; a copy-only overlay would leave removed catalog seeds and photos behind. Exclude both repositories' Git metadata, planning/provenance documents, local credentials, runtime state, dependencies and generated output.
  4. Validate the project ID and bindings, then install/configure the publishing checkout for its execution profile and run relevant checks. Use the bundled Sites publishing workflow with the retained opening result, remaining checks/build and an archive path. It commits and pushes that checkout through the existing Sites history; never rewrite the published branch.
  5. Save/deploy the exact returned source commit and archive using native Sites tools only when the release is ready. Preserve the current restricted audience until the migration's privacy gates pass. Record the GitHub commit, Sites commit, version and deployment result together in the release record.

Source import alone performs none of these publication operations. Changes made directly in Sites after synchronization must be brought back into GitHub before the next release; avoid parallel implementation in both repositories.

Windows publishing setup verified during step 5: use the installed pinned pnpm JavaScript entrypoint through process-scoped SITES_PNPM_BIN; add installed Git Bash to that publishing process's PATH; set TAR_OPTIONS=--force-local so GNU tar treats a Windows drive path as local. When the sandbox and network-enabled process have different Windows owners, apply a process-scoped Git safe.directory exception only to the exact publishing checkout. Do not relax global Git trust or persist repository credentials. Reuse the existing package cache with an explicit local store directory when installing; frozen-lockfile verification must complete successfully.
