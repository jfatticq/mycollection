Step 2: data model and access controls

Implemented locally October 5, 2026. Migration plan · Target requirements

Implemented foundation

The additive migration drizzle/0002_hard_scorpion.sql creates sixteen normalized tables alongside the four legacy tables. It does not import, backfill, drop or clear legacy records. Existing applied SQL and snapshots remain unchanged.

  • Users, provider identities, explicit administrator grants and one private-default collection per user.
  • Catalog releases, taxonomy associations, related-release links, nested stable part occurrences, file-card text and catalog revision snapshots.
  • Separate owned-copy records, confirmed/parts-only/unconfirmed ownership, condition, completeness, packaging, nullable sealed state and private acquisition details.
  • Release-scoped owned-part quantities and unidentified parts. Unknown is null; absent is zero. Expected part quantities are absolute totals per one release, not multiplied by nesting.
  • R2 media metadata, owner/collection scope and ordered links to releases, parts, file cards or owned entries.

Database foreign keys, uniqueness constraints and checks enforce collection uniqueness, nonnegative quantities/prices, part-to-release associations, ownership states, and packaging presence for Complete. Catalog saves reject indirect part cycles and preserve removed catalog parts as retired records. Existing owned quantities for retired parts survive subsequent entry saves.

Server authorization

Sites-dispatched user IDs identify collectors; email no longer grants permissions. Registration creates one private collection and a neutral display name, never an email-based public name. Deleted identities are denied access. Concurrent first requests converge on the same user/collection.

Collection reads and mutations are constrained to the authenticated user's collection. Other signed-in users can read a public collection through an explicit collection ID; anonymous users cannot. Those public responses omit notes, location, acquisition date, purchase price/currency/source and email. Administrator status does not grant access to another collector's private collection.

Photo metadata authorizes every R2 read. An unlinked collection upload remains private even when its collection is public. Linked collection media requires the owner or a signed-in viewer of the currently public collection. Catalog media becomes anonymous-readable only after an administrator links a catalog-scoped upload to a catalog subject. Private uploads cannot be reclassified into public catalog photos. Protected responses use private, no-store caching.

Mutation endpoints verify origin. Uploads check permitted type, size and image signatures, use generated object keys, and compensate with R2 deletion if the metadata write fails. Full image decoding, location-metadata stripping, rate limits and polished upload forms remain launch work in step 4.

Administrator setup before deployment

Required deployment configuration: Set the server-only runtime value ADMIN_CHATGPT_SUBJECT to the owner's exact verified oai-authenticated-user-id for this Site. Do not substitute a login email, workspace account ID, hosting project ID or a subject from another Site.

  1. Keep the deployed Site owner-restricted while preparing the later release.
  2. Use the owner's authenticated /api/account response to verify identity.subject after the new schema and routes are deployed.
  3. Configure the exact subject through native Sites runtime environment management. Its next authenticated request creates the explicit admin role row.
  4. Verify that this account can save a catalog release and another collector cannot. No first-user or email fallback exists. If the setting is absent, catalog writes fail closed.

The setting is intentionally blank in the local environment template. This step did not configure a production subject, change Sites access, apply production migrations or deploy. To revoke a bootstrap grant, clear/change the setting and remove the corresponding role row; removing the row alone while the matching setting remains would regrant it on the next sign-in.

API foundation

EndpointImplemented behavior
GET /api/accountOwn user/collection IDs, role and verified provider subject. Requires sign-in; no email returned.
GET /api/catalogAnonymous D1 catalog search/list; ?id=… returns release, parts, file cards and linked catalog images.
POST /api/catalogAdministrator-only save of {release: …}, immediately published. Existing releases require expectedRevision. Captures revisions and retires omitted parts.
GET /api/collectionOwn records/preferences, or signed-in public collection via ?collectionId=…. Public projection excludes private facts.
POST /api/collectionOwn save/delete/preferences/visibility actions. Saves one copy with normalized parts and optional owned photos. Client-supplied collection ownership is rejected.
POST /api/photoAuthenticated multipart upload; collection scope by default, catalog scope restricted to administrator.
GET /api/photo?id=…Rechecks media ownership, linkage and current visibility before reading R2. Legacy objects without metadata are unavailable.
POST /api/media/linksLink own uploads to own entries; administrator can link separately uploaded catalog media to catalog subjects.
Legacy catalog audit endpointsUse the same explicit administrator guard and private response caching.

New collection saves use parts with partId and nullable quantity, separate unidentifiedParts, and structured private purchase fields. Quantity is always one copy. Complete initializes verified expected parts and original packaging for a new entry without inferring sealed status or Mint condition. Partial and Not sure leave unspecified quantities unknown.

Validation and remaining work

scripts/check-step2.cjs runs the generated migrations and actual route handlers against real in-memory SQLite and an isolated R2 test adapter. It verifies stable identities, private defaults, role restrictions, cross-user read/edit/delete denial, public field projection, immediate media revocation, separate copies, null/zero quantities, catalog revision conflicts/cycles, retired-part preservation, upload compensation, deleted-user denial, foreign keys and query indexes. It also checks that an existing legacy row survives the additive migration.

TypeScript validation and existing catalog, accessory and photo domain checks pass. The portable production build also passes, with the inherited large-chunk and route-classification advisories. These are local checks, not claims about deployed public access or provider feasibility.
