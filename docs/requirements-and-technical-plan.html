Purpose and audience

Build with OpenAI Sites in this GitHub repository. Provide a complete reference catalog of G.I. Joe figures, vehicles, playsets, accessories, and related items; personal collection tracking; condition-sensitive price estimates; and, later, collector-to-collector commerce and discussions.

Confirmed: The owner will test with personal research and an actual collection. Launch must also support other users signing in and tracking their own collections. Anonymous visitors can browse only the reference catalog. Signed-in collectors can view public collections and aggregate counts of items in public and private collections, without access to other users' private collection details.

Confirmed design: Use a restrained military-inspired collector interface. Support desktop and mobile fully, prioritizing desktop for the owner's main workflow; make photo uploads and parts checklists usable on phones.

Platform constraint verified October 5, 2026: Current Sites documentation prohibits enabling financial transactions. Commerce cannot be implemented on Sites under this restriction, including assuming hosted payment checkout is a workaround. Preserve the desired marketplace requirements for a separate supported host or a future platform policy change. Official Sites documentation.

Confirmed functional requirements

Reference catalog

  • Only the site owner can create or edit reference catalog records.
  • Provide an owner-only catalog editing form and bulk import from CSV and JSON.
  • Catalog entries have a single published state. Successfully saved entries are immediately visible in the reference catalog; no draft/publish workflow is required.
  • Corrections to a published parts list update the reference catalog immediately. Flag affected collection entries for collector review while preserving their recorded quantities.
  • Retire catalog entries from new additions instead of deleting records referenced by collections. Preserve existing holdings and their reference details.
  • Provide owner-only merging of duplicate catalog entries, preserving individual copies, quantities, photos, notes, and history. Retirement is an availability setting, not a draft or publication workflow.
  • The owner handles catalog research and data preparation independently. AI-assisted catalog entry is outside this implementation plan.
  • Catalog fields and applicable search/filter controls include name/character, item type, release year, toy line, series/sub-series, wave, scale, faction, country/market, manufacturer, product number/UPC, and original retail price.
  • Each catalog item supports an array of images and a parts list. Variant is a relationship linking to another catalog item entry, rather than a free-text variant field.
  • Each identifiable release has its own catalog record, including repaints, packaging variants, and international releases. Related records are linked together.
  • Capture each item's parts with names, expected quantities, and part images.
  • Include the primary figure, vehicle, or playset in the parts model so its owned quantity can be zero independently of accessories.
  • A multipack uses the same item-and-parts model as a vehicle with a pilot/driver or a figure with weapons and gear. Its included figures and vehicles are parts; owning the multipack does not require owning every included part. Parts support sub-parts, such as a figure's helmet and rifle, with independently tracked quantities. Links to other figure releases remain to be defined.
  • Support optional file cards, including images and actual text.
  • Other websites are research references, rather than a single authoritative or complete catalog. User-named sources: yojoes.com, 3djoes.com, actionfigure411.com, toys.hisstank.com, and others. Source URLs and reuse permissions have not been verified.

Personal collections

  • A signed-in collector searches the reference catalog and adds a catalog item to their own collection.
  • Each user has exactly one collection, with one collection-wide public/private setting.
  • Use ChatGPT sign-in at launch. Support Microsoft and Google login soon afterward, pending verification of platform capabilities and the intended login flow.
  • Use a public collector display name while keeping login email private. Never expose login email in public profiles, collections, discussion posts, counts, or responses to other collectors.
  • At launch, collectors can export their own data and delete their account. Account deletion removes their collection, photos, and profile. Once discussions exist, retain posts under Deleted collector with personal details removed. Deletion confirmation, processing time, and backup retention must be specified before implementation. Transaction retention will be addressed before any future commerce launch.
  • Track every owned copy separately, allowing different conditions, missing parts, photos, and other details for copies of the same catalog release.
  • Collections default to private. The owner can make a collection public when creating it or change its visibility at any later time.
  • Anonymous visitors cannot browse personal collections, including those marked public. Public collection browsing requires sign-in.
  • Signed-in collectors can see aggregate item counts from both private and public collections, but cannot inspect another collector's private collection or attribute private holdings to that collector.
  • Additional details such as condition and parts are optional when adding an item.
  • Each owned entry supports optional photos, notes, acquisition date, purchase price and currency, purchase source, and storage location.
  • Collection search supports catalog metadata plus condition, completeness, missing parts, storage location, and needs-review status.
  • Always show the search control. Keep filter options collapsed by default and allow the user to expand them.
  • Provide a view of catalog releases the collector does not own. Include releases with parts-only holdings and unconfirmed ownership using appropriate labels. An owned but incomplete multipack is owned for this view, just as a vehicle without its driver or a figure without its weapon is owned.
  • Support collection import and export at launch in CSV and JSON, including individual copies and part quantities. Provide downloadable templates collectors can fill out. Handle photos separately from the data templates.
  • For a public collection, other signed-in collectors can see items, parts, conditions, and photos. Purchase information, storage locations, and private notes remain owner-only. Recommended default: acquisition dates are also owner-only.
  • Adding an item offers a quick choice: Complete, Partial, or Not sure. Complete assumes original retail packaging and all expected parts present; Partial and Not sure initialize quantities as unknown, rather than zero.
  • Unknown quantity and confirmed zero are distinct states. Collectors can refine quantities and details after adding the item. Complete does not imply sealed or any particular physical condition.
  • Offer an optional overall condition grade: Mint, Excellent, Good, Fair, Poor, or Unknown. Provide tooltip guidance for each grade to help collectors choose, accessible through keyboard focus and a tap on touch devices.
  • Allow optional defects and notes on individual parts, such as discoloration, broken tabs, and loose joints. Parts may have their own condition grades.
  • Track boxes, cardbacks, file cards, instructions, and inserts individually, with presence/quantity and their own condition. Track sealed, opened, or unknown status separately.
  • Complete means the item is in its original retail packaging with all expected parts present; this includes boxed and blister-carded releases. Anything less is not complete, including loose items with all toy parts present. Sealed status is recorded separately.
  • Collectors can record owned quantities of individual parts, including zero for the primary object and all other parts. Example: an entry for Snow Job can contain two skis, zero figures, and zero other parts.
  • Collectors can track loose weapons and accessories independently when their associated catalog release is unknown. How these entries become associated with an identified release remains open.
  • Catalog items show figures/sets owned separately from parts-only holdings. Each category shows total owned counts split between public and private collections, plus its distinct collector count. A collector with only Snow Job's skis belongs in the parts-only category. Private owners are not identified.
  • Entries with unconfirmed item ownership appear in a separate Ownership unconfirmed category until item ownership or a parts-only holding is confirmed. They do not inflate confirmed ownership totals. Missing or unknown quantities for some multipack contents do not invalidate otherwise confirmed ownership.
  • Later, collectors can submit a photo to receive likely catalog matches.

Photo identification

  • Initially identify a single figure, vehicle, other catalog item, or loose accessory. Identification of multiple objects in a group photo is deferred.
  • Present ranked catalog candidates with comparison images and reasons for the match.
  • The collector must confirm a candidate before an identified entry is added. Do not automatically assign a catalog release or infer all parts present from a photo.
  • Allow uncertain results to be saved as unidentified inventory with the submitted photo. Support later identification and association with a catalog release or part.

Valuation and commerce

  • Estimate prices for whole figures, vehicles, sets, and individual parts, reflecting condition and completeness. Whole-item and part-level valuation are the working scope; the user's preference for both was tentative.
  • Show each collector an estimated total value of their collection. A graph of estimated collection value over time is desired.
  • Use USD for valuation displays at launch, retaining the original currency of source evidence.
  • Take weekly collection valuation snapshots. The historical chart shows the estimated value of holdings owned on each snapshot date, with acquisitions and removals marked to distinguish inventory changes from market movements.
  • Only the site owner manages shared manual valuation evidence. Collectors can privately override estimates for their own holdings; label personal overrides separately from market estimates.
  • Use a combination of completed sales, current asking prices, and manually entered research from eBay and similar sites. Specific integrations and permitted data access remain unverified.
  • Present estimates as a range with currency, valuation date, condition/completeness assumptions, supporting comparisons, and a confidence indicator. Show Insufficient data when evidence is too sparse.
  • Allow collectors to offer collection items for sale and purchase from other collectors.
  • Initially restrict marketplace sellers, buyers, and shipping addresses to the United States.
  • The owner handles listing moderation and user reports. Sellers handle shipping and returns. A payment provider handles payment processing and seller payouts; exact dispute, loss, and tax responsibilities depend on the selected configuration.
  • Planning assumption: charge a seller-paid 5% commission on the item subtotal, excluding shipping and tax, with payment processing charged separately to the seller. Validate operating costs before commerce launch.
  • Initial listings use fixed prices, with one seller per checkout.
  • Support sales of whole collection entries and individual parts in specified quantities, allowing the seller to retain the remainder of an entry.
  • Sellers set shipping charges, buy shipping labels themselves, and enter tracking on the order. Built-in label purchasing is deferred.
  • After successful payment, show a purchase as Incoming. Add it to the buyer's owned inventory only after the buyer confirms receipt; exclude incoming purchases from confirmed ownership counts and owned collection valuations.
  • Evaluate marketplace approaches that reduce the owner's operational burden and liability; recommendations require current provider research before selection.

Accepted return and issue-resolution policy

  • For change-of-mind returns, sellers choose No change-of-mind returns or Returns within 14 days of delivery. Display the choice before checkout and retain its version on the order. If offered, require return in the received condition; buyer pays return shipping and original shipping is not refunded unless the seller offers better terms.
  • Regardless of the change-of-mind choice, require a resolution path for non-delivery, wrong items, undisclosed damage, or materially inaccurate descriptions. Remedy: seller-funded return where applicable and refund of the item price and original shipping, or a mutually agreed partial refund.
  • Ask collectors to report delivery/description issues within 30 days of delivery or the latest expected delivery date, and require sellers to respond within three business days. These are site service targets, not limits on statutory rights or payment dispute deadlines.
  • The owner facilitates unresolved cases and can remove listings or restrict sellers; do not promise that the platform funds seller refunds or guarantees reimbursement.
  • Refund the site's commission proportionally when the item price is refunded. Processing-fee treatment follows provider terms and must be disclosed.

Preserve listing photos/descriptions, accepted policies, messages, tracking, and refund records for issue resolution. Stripe provides chargeback tools, but the issuing bank decides the outcome; the site's process cannot override that decision. Stripe dispute guidance.

Define shipping promises and delay/cancellation handling before commerce launch. FTC guidance requires shipment as promised, or generally within 30 days if no time is promised, with delay notices and cancellation/refund options where applicable. Final policy must account for applicable consumer requirements. FTC shipping guidance.

Discussions

  • Support discussions at both site and individual catalog-item level for signed-in users.
  • Only signed-in collectors can read discussions. Posts appear immediately without pre-publication approval.
  • Provide post reporting and owner moderation after publication.
  • Support multiple titled threads per catalog item and site-wide topics, with replies in chronological order. Item threads appear in the site-wide feed with an item label and link.
  • Item discussions must also appear in the site-wide discussion view while retaining their item scope and association.
  • Recommended model: display the same item thread in both views rather than copying posts; enforce sign-in on both views and their APIs.

Notifications and buyer/seller messaging

  • Provide in-app notifications. Send email for purchases, shipping updates, and return issues during the commerce phase.
  • Offer optional email notifications for replies to followed discussions. Catalog correction alerts appear in-app.
  • Keep buyer/seller messaging attached to listings and orders. Messages are visible only to participants and to the owner when needed for a reported issue.
  • General private messaging is deferred.

Recommended relational data model

Use stable opaque identifiers rather than titles, UPCs, or URLs as foreign keys. Money uses integer minor units plus currency; quantities are nonnegative integers or null for unknown. External product identifiers may be absent or reused, so they are not assumed globally unique. Dates should distinguish known acquisition dates from the date data was recorded.

Parts quantity convention: Recommended expected quantities are absolute totals per one retail release, even for nested parts; nesting groups them visually and does not multiply totals. If a set contains two identical figures, expected helmet quantity is two, not a quantity that is multiplied again during valuation or import. Document this in templates.

Confirmed multipack ownership convention: Use the same item-and-parts model as figures and vehicles. Count a confirmed owned multipack entry once even when included figures, vehicles, or accessories are missing; do not require every figure to meet its expected quantity and do not treat incompleteness as lack of ownership. Each owned copy remains a distinct entry. Complete still requires original retail packaging and every expected part.

Recommended classification implementation: Keep confirmed item ownership, parts-only holdings, and unconfirmed ownership separate from completeness. A multipack with confirmed included figure/vehicle ownership can count as an owned item despite other unknown quantities. Accessories alone can remain parts-only, consistent with the Snow Job skis example. Do not add component counts to the number of owned multipack entries or automatically create standalone figure holdings from their contents.

Merge procedure: Preview impacted entries, map corresponding parts explicitly, retain separate owned copies, and require a mapping decision for conflicts. Preserve unmatched legacy parts and flag review rather than guessing or discarding quantities. Redirect the duplicate's reference to the surviving record without erasing provenance.

Create indexes around catalog filters, collection/user lookups, owned-entry part joins, thread scope/time, and evidence subject/date. Verify representative query plans and avoid redundant indexes. Use foreign keys and check constraints; schema changes use inspected migration files rather than runtime table creation.

Recommended service and API boundaries

  • Catalog: Public read/list/detail services; signed-in holdings aggregates; owner-only create/update/retire/merge/import services. Search uses parameterized queries and paginated results with a stable secondary sort key.
  • Collection: Own create/edit/remove entry and part operations, own visibility setting, own imports and exports; separate sanitized public-collection reads. Derive owner identity from the session, never from an editable request field.
  • Media: Upload validation and authorized retrieval by media identifier. Recheck current collection visibility on each protected retrieval; strip location metadata from collector photos.
  • Account: Profile update, comprehensive own-data export, deletion request and status. Export records as versioned JSON plus CSV tables, with a separate downloadable media archive or authorized file manifest.
  • Community: Signed-in feed/thread/post/follow/report APIs and owner-only moderation. Item feeds and site feeds reference identical thread IDs.
  • Identification/valuation: Server-only provider adapters, per-user quotas, asynchronous job status where necessary, manual evidence admin, private overrides, and weekly snapshot generation. Provider secrets never reach the browser.

Validate all mutations on the server, use request-origin/CSRF protections appropriate to the platform auth model, optimistic concurrency for edits, and idempotency identifiers for imports and long-running jobs. Return field/row errors rather than silently coercing unknown quantities or invalid identifiers. Keep transactions bounded and use database batch operations where atomicity is needed.

Import contract

Recommended CSV downloads are a coordinated set of files for entries, parts, and relationships, joined by template keys. JSON carries the same information as nested objects. Include example rows, enum documentation, required identifiers, and empty-as-unknown guidance. Photos are uploaded separately and mapped using entry keys.

Imports never merge owned copies simply because release IDs match. New rows create distinct entries; explicit existing entry IDs permit updates only within the actor's collection. Owner catalog imports update by stable catalog ID or import key. Repeating the same committed import must not duplicate holdings. Preview errors/conflicts before commit; an import staging screen is not a catalog draft publication state.

Proposed condition tooltip copy

These are collector-facing descriptive grades, not professional grading certification. Completeness, packaging, and sealing are separate. Apply a grade to the object being assessed; a mint figure can have a poor box.

GradeTooltip guidance
MintNo visible wear, damage, or discoloration on inspection. Record any known defect separately. Does not imply sealed packaging.
ExcellentVery slight wear visible on close inspection; no significant damage. Note minor paint rubs or other defects.
GoodNoticeable wear or small defects, but the item remains usable/displayable. Describe paint loss, discoloration, or loose joints.
FairSubstantial wear or damage that affects appearance or function. Describe cracks, broken tabs, repairs, or heavily worn joints.
PoorSevere wear or damage; significant repairs may be needed or the item may be suitable mainly for parts.
UnknownNot inspected or not enough information to choose a grade. You can update this later.

Privacy, deletion, and operational safeguards

  • Configure a public Site for anonymous catalog access, then require verified identity on all collector/community surfaces. Grant catalog administration only to the owner's verified identity; email/display name is not an authorization key.
  • Test field-level access with anonymous, collector A, collector B, and owner sessions. Private holdings contribute only to approved aggregates; no per-user private breakdowns or arbitrary owner filters.
  • Sanitize discussion formatting and file-card content; enforce upload MIME/type and size checks, image decoding, rate limits, and non-executable media responses. Proposed launch limit: ten images per entry, 10 MB per uploaded image, pending platform limits and owner review.
  • Hide login email everywhere outside the user's account and narrowly authorized operational access. Account deletion removes collection records, media, private valuations, subscriptions, and identifying profile fields from active storage; retained discussion posts use Deleted collector.
  • Scrub personal details in retained discussion text, attachments, and revisions; flag ambiguous content for owner review. Merely renaming the author is insufficient. Use a resumable deletion job for storage cleanup and revoke app access immediately.
  • Verify supported backup/export and restoration procedures before public launch. Keep code, migration history, catalog data, and media recoverable independently; restoring a backup must reapply deletion records so removed accounts are not resurrected.
  • Recommended targets: remove active collection/profile data within seven days of deletion request; expire any application-managed backup copies within 30 days. These are proposed targets, not claims about Sites-managed backups. Publish only retention commitments verified with the platform.
  • Use redacted server logs and track save/import/upload failures. Do not log login tokens, full private notes, image bytes, or provider keys. Collect only operational telemetry needed to diagnose the application.

Acceptance scenarios and release gates

  1. Anonymous access: Browse catalog photos, filters, variants, parts, and file cards; collection records, holdings counts, private media, discussions, and admin mutations are inaccessible.
  2. Catalog authority: Collector sessions cannot create, edit, retire, merge, or import catalog data by calling APIs directly. Owner saves publish immediately.
  3. Separate copies: Add two copies of the same release with different condition/parts/private details; editing or removing one does not change the other.
  4. Quick addition: Complete initializes original packaging and expected parts without inferring sealed or Mint. Partial/Not sure preserve unknown quantities. Blank, null, and zero round-trip correctly through imports/exports.
  5. Snow Job skis: Set two skis, zero primary figure, and zero other parts; count as parts-only and keep the release in the unowned view. Unknown primary quantities show Ownership unconfirmed.
  6. Multipack: An owned multipack with a missing included figure still counts as one owned entry and is excluded from the unowned view, but is not Complete. Track figures, vehicles, and their accessories independently; an accessory can exist without its parent figure. Do not multiply absolute expected quantities, count each included figure as a separate owned set, or double-count parts in estimates.
  7. Privacy: Public collection responses show permitted fields only. Switching to private revokes later reads and protected media access. Email, private notes, purchase facts, and storage location never leak to another collector.
  8. Counts: Split public/private holdings by the agreed categories; deduplicate collectors within each category; exclude unconfirmed holdings from confirmed totals.
  9. Correction/merge: Rename, add, remove, retire, and merge catalog records without losing owned quantities or copy identities. Affected entries show review flags; new parts remain unknown until reviewed.
  10. Imports: Templates download; valid CSV/JSON produce equivalent data. Invalid IDs, negative quantities, cross-user IDs, cycles, and conflicting merges produce actionable errors. Retrying a committed job does not duplicate holdings.
  11. Export/deletion: Export the user's records and media mapping; delete an account and confirm its data/media are unavailable. Restore rehearsal does not restore deleted users. In phase 2 retained posts show Deleted collector with identifying content removed.
  12. Community: Signed-in posts appear immediately. An item thread is the same thread in both feeds. Reports and moderation work; anonymous requests cannot read post bodies.
  13. Identification: Rank only existing catalog candidates, show comparisons/reasons, preserve uncertain inventory, and add/associate only after confirmation. Missing catalog coverage does not produce an invented match.
  14. Valuation: Separate asking/sold evidence and private overrides; sparse coverage says Insufficient data. Item/part totals do not count the same holdings twice. Weekly snapshots retain history after acquisitions, edits, and removals.
  15. Usability: Verify desktop and mobile search, collapsed filters, part checklists, photo upload, keyboard/tooltips, readable error states, and 200% text enlargement.

Proposed test dataset: At least a dozen representative owner-provided releases across both initial lines, including variants, an international/packaging distinction, a nested multipack, a vehicle, file cards, and one retired/merged test record. Include complete, loose, damaged, parts-only, unknown, duplicate-copy, and unidentified holdings across two test collectors. This is a testing recommendation, not a requirement to complete either toy line before launch.

Use focused tests for ownership/privacy, quantity/statistics rules, merges/imports, and deletion. Verify responsive workflows manually on representative devices and perform a production build and migration checks. Set performance targets after measuring the representative dataset; do not promise unmeasured capacity.
