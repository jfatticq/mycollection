Import and merge contracts

Version 1 format guide documents CSV columns, nested JSON cells, unknown versus zero, grades, dates, currencies, identifiers and separate photos. Imports accept 1–50 rows and 2 MB, with additional nested-part/database-statement bounds. A missing ID creates a new copy/release; an existing ID updates it. Start from exports when replacing existing fields. Photos are not overwritten by data imports. Preview IDs are bound to the submitting user, expire after 30 minutes and commit once. Catalog cross-release links work within one import. Validation is repeated before the atomic write so stale references fail without partially committing a file.

Duplicate merging requires an explicit decision for every source part: map it to a unique target of the same kind, or preserve it as a retired historical part. Separate copies, null/zero quantities, conditions, defects, photos and private facts are preserved. Catalog reference photos/file cards and taxonomy/relationship links move to the survivor. The duplicate retires and redirects to the survivor. Complete copies become Partial pending review. The transaction snapshots live quantities and checks catalog revisions, so concurrent changes are preserved or rejected safely. Database triggers prevent stale saves from putting holdings back on a merged release.

Uploads and request limits

The browser accepts JPG/PNG/WebP under 8 MB, resizes the longest edge to 1800 pixels and converts to JPEG. The server fully decodes JPEGs with a four-megapixel and 48 MiB decoder allocation cap, then encodes a fresh pixel-only image. Source EXIF/comments and location metadata are not retained. SVG and corrupt/truncated files are rejected. Request bodies are bounded while streaming. Authorized delivery retains no-store caching and non-executable response headers.

The portable Worker-compatible implementation uses jpeg-js; its synchronous CPU cost and the actual Sites Worker limits still require a production-capacity benchmark. No external model/API image service is used. D1-backed request windows survive process restarts: uploads 30/hour, imports/previews/commits 30/hour, collection writes 120/minute, catalog/taxonomy writes 60/minute, profile writes 30/minute and merges 20/hour. Ten-image collection limits apply to editing and direct links.

Deletion and recovery

Typed confirmation immediately revokes access, removes identities/roles, collection rows, media metadata, staged imports and identifying profile fields, and retains a minimal hashed-user tombstone. Shared catalog contributions/reference photos remain archived under a system catalog identity. R2 cleanup is durable and resumable in batches of twenty files. A deleted collector can reopen Settings to retry cleanup; the administrator can retry pending jobs without seeing private collection contents. Storage outages do not restore media visibility.

A minimal deletion ledger is also written to private R2, independently of D1. A restore rehearsal re-creates pre-deletion database records, reapplies that ledger and verifies access is still denied. Before a real database restore, restrict Site access and persist pending deletion-ledger writes, or independently export the current tombstones/jobs while storage is unavailable. Do not replace that state with an older database until those records are recoverable. Then restore/apply the schema, reapply every ledger page through maintenance, finish pending cleanup, and only then reopen access. Back up the deletion ledger independently with the catalog/media recovery procedure. No data export is presented as a full backup.

Application rows are removed during the confirmed request; storage failures leave a pending cleanup job for retries. No unverified Sites-managed backup expiry is promised. The proposed seven-day active-storage and thirty-day application-backup targets require an operational retry/backup process and platform verification before publication. Automated background cleanup has not been configured.
